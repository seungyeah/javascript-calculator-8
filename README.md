	- ## 과제 분석
		- 본인 상태 : AI 없이 코딩하던 시절엔 C 언어만 다뤘음.  AI가 등장하고 웹개발 할 수 있을것 같아 패기롭게 도전. 3년간 바이브 코딩 진행.
		- 요구사항을 어떻게 이해했나.
			- 문제: 숫자와 구분자로 조합된 문자열이 입력으로 주어지면, 숫자 부분만 추출하여 더하라.
			- 구분자가 될 수 있는 것: 콜론, 콤마, //와 /n사이의 문자
			- 유의 사항: 양수 있다고 가정. (음수 처리 안 해도 됨)
			- 에러 처리: 사용자가 구분자 아닌 값을 입력하는 경우. (=>"[Error]"만 반환해도 됨)
		- 방향: 기본 구분자, custom 구분자 등록 -> 문자열에서 각 문자를 iter하며 숫자인지 확인 -> 숫자가 아니라면, 구분자인지 확인 | 숫자라면, tracking_sum에 *10하여 더함 (end) -> 구분자라면 total += tracking_sum; tracking_sum = 0 | 구분자가 아니라면 Error 반환
		- 고민:
			- 문자열 순회 방법
				- for (const ch of "string") {
				      // ch = "s" → "t" → "r" → "i" → "n" → "g"  
				  } 가능함  
				- 신기한 부분: js엔 char 타입이 없어서 각 문자도 문자열임
			- 구분자인지, 숫자인지 판단하는 방법
				- ascii 문자 비교
		- 예외 및 가정:
			- 사용자가 설마 구분자로 숫자를 두진 않겠지?
			- 구분자가 등록됨을 어떻게 알지? => // 발견 시 구분자라고 생각 -> /n 발견시 등록
				- 입력이 "//\n"이면 구분자가 ""가 되는건가? 이것도 에런가?
			- 구분자는 한 글자인가? 여러 글자도 가능한가?
			- => 구분자는 한 글자이며, 숫자가 아니며, "//\n"은 구분자를 등록하지 않았다고 가정.

	- ## 과제 진행 소감
		- 느낀 점:
    		- 생각보다 고려해야할게 많았다.
    		- 사실 양심 고백을 하자면 개발 편의성을 위해 구분자는 한글자이며 숫자가 될 수 없다는 조건을 추가했다. 하지만 이것은 매우 훌룡한 기능이다.
        		- 만일 두 글자 이상을 구분자로 사용한다면, 이는 귀찮음을 커지게 할 뿐이다. 세상에 기호는 많다. 그 기호중에 하나를 골라 구분자로 사용하면 된다. 굳이 매번 두 글자 이상을 입력하며 숫자를 구분 할 필요는 없다.
        		- 구분자를 숫자로 두는것은 사용자 입장에서도 더 큰 혼란을 야기시킬 뿐이다. 계산 결과를 검증하기도, 예측하기도 힘들어진다. 
		- 배운 점:
			- commit 메세지 작성 방식
    			- 요약
        			-` <type>(<scope>):<subject> \n\n <body>`

            			- type: feat, fix, docs, style, refactor, test, chore
            			- scope: 변경이 일어난 영역 (docs, ui, build, api, parser, ..)
            			- subject: 명령형, 현재형, 소문자 시작, 마침표 없음
          			- 중요하지 않은 commit은 type을 chore, style, docs등으로 추가하여 추후 bisect 및 changlog 작성 시 거를 수 있음. 
      			- 의문: 실제 진행해보니 type, scope를 모두 어떻게 잡아야 할지 잘 모르겠다. 
        			- 이번 프로젝트는 commit에 담아야 할 내용을 README.md의 진행 로그에도 담았다. commit 클릭하면 README에서 어떤 부분을 어떻게 바꾸었는지 대략적으로 확인하고 code 상에서 직접 확인하면 좋을 것 같았다. 또한, 이렇게 하니 scope를 어떻게 잡을지 몰라 변경한 파일 이름으로 두었다.
        			- 하지만 이 방식은 개인 혼자서 프로젝트를 하는 경우에만 좋고, 협업할 때는 사용 할 수 없는 방식이다. 
        			- 다음 프로젝트부터는 규모가 커지므로 type을 분리해야겠다. 근데 그렇게되면 commit 메세지가 너무 많이 올라갈것같은데... changelog에 올릴것과  올리지 않을것을 구분하고 changelog를 작성하는데 초점을 맞춰야겠다. 
			- 테스트 코드 실행시, Error가 발생했을 경우 메세지도 정확히 일치해야하는줄 알았는데, 아니라서 신기했다. 심지어 expect(app.run()).rejects.toThrow("")로 두어도 테스트가 통과한다. 
    			- Jest의 toThrow() 동작 방식:
                	- toThrow() (파라미터 없음): 어떤 에러든 발생하면 통과
                    - toThrow("") (빈 문자열): 어떤 에러든 발생하면 통과 (빈 문자열은 모든 문자열에 포함됨)
                    - toThrow("특정 메시지"): 에러 메시지에 "특정 메시지"가 포함되면 통과
                    - toThrow(new Error("정확한 메시지")): 에러 메시지가 정확히 일치해야 통과
            - npm start 명령어로 직접 string 입력값을 전달할 경우 \n을 구분자 선언 클로징으로 사용하고, npm test로 전체 테스트를 진행할 경우 \\n을 구분자 선언 클로징으로 사용한다. 어떤 차이가 있나?
                - 터미널(실행, npm start): 사용자가 //\n1,2,3를 타이핑하면 \와 n이 문자 그대로 들어간다. 즉 프로그램이 받는 건 //\\n1,2,3(백슬래시+n)이다.
    			- 테스트 코드(npm test): JS 문자열 리터럴에서 "\n"은 진짜 줄바꿈이다. 만약 테스트에 "//\n1,2,3"를 넣으면 입력 한 줄이 두 줄로 쪼개져 readLineAsync()가 두 번 읽게 된다. 그래서 **문자 그대로 \+n**을 전달하려면 리터럴에서 **"\\n"**로 써야 한다. ("\\n" → 실제 값은 \와 n)
		- 많은 시간을 투자한 부분:
    		- 어떤 예외 상황이 발생할 수 있을지에 대한 고민
    		- 슬래시, 역슬래시를 구분자로 사용하는 경우에 대한 처리
    		- escape 규칙에 대한 이해.
